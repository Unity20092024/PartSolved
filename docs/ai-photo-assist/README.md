# AI Photo Assist — Stage 1 (private development)

## Status and boundaries

Implemented on an isolated branch from main `ad48012`. The repository and open-PR audit on 2026-11-09 found no blog implementation branch, Supabase configuration or PartSolved database. The connected Supabase account contained only an unrelated project; it was not touched. There is no paid infrastructure provisioned, hosted migration applied, merge, push or deployment in this work.

Stage 1 is **not released**. `reviewEnabled()` always refuses Vercel production, regardless of cookies or flags. Local review requires `AI_LOCAL_REVIEW=true`; Vercel preview review requires `VERCEL_ENV=preview`. Both also require the explicit enable flag, strong review secrets and a server-verified six-hour HttpOnly session. Default public behavior is unchanged. Public release needs a separate, reviewed change after evaluation, privacy and security sign-off; do not remove the gate just to make a preview work.

The existing Guided Finder, photo capture/upload, Add Details, all per-type measurements, review, recovery assistance, category photographs, Guides and video behavior remain. Exact supplier matching, compatibility, prices, checkout and Strybuc integration are outside Stage 1.

## What was added

- `/api/hardware/analyze`: server-side OpenAI Responses request with a pinned, approved model, strict family enum/schema, independent runtime validation and Unknown recovery. No tools, web search or supplier lookup.
- `/api/hardware/review`: rate-limited reviewer session creation and session termination. This is temporary private development access, not customer authentication or a replacement for the future blog's administrator Auth.
- `/find-part/ai-review`: noindex reviewer sign-in and authenticated usage monitor. Returns 404 by default. Usage shows UTC daily/monthly allowances, requests, unreconciled reservations and overruns.
- Reviewer-only `PhotoAssist` inside the **existing** Guided Finder/assistance and photo-preview pages. One initial photo plus up to two optional views can be selected; existing four supporting-photo capacity is unchanged. Additional views are not automatically transmitted.
- Explicit consent before every photo set; bounded client compression; second server validation/re-encoding; memory-only image handling. Existing originals are retained locally. Shared workflow privacy notices switch to the AI consent explanation for reviewers and after an analysis request, so Add Details/Review never falsely claim that a requested photo transfer was impossible.
- Customer review of possible families, short visible observations, uncertain markings, explicit provisional missing-measurement prompts derived from the existing part-type configuration, and guide links. Markings are not automatically copied into manual fields. There are no inferred numeric measurements.
- Acceptance first presents a confirmation explaining category/type changes; it preserves manual brand, markings, finish, orientation, problem, measurement notes and all per-type measurement entries. Rejection adds to existing assistance exclusions. Unknown leaves manual intake intact. Original questionnaire answers remain available.
- Extra-only photo intake can reach Add Details: after explicit family confirmation (or choosing Review Identification Details for an Unknown outcome), the first selected photo becomes the primary part photo only when none exists. Existing primary photos are kept. Skipping AI with no primary photo collapses the panel and leaves the manual questionnaire available; it does not route into empty-photo recovery.
- Client-navigation state survives while the root provider is mounted. Refresh/tab close clears it. Replacing the primary photo clears analysis; changing/removing the selected image set prevents accepting stale results. Cancellation may not prevent provider billing.

## Shared database coordination (required before live review)

Use **the same Supabase project and migration history as the blog**. No Supabase client SDK, auth migration, storage bucket or competing database configuration was introduced. Runtime accounting uses Supabase's HTTPS Data API with a server-only secret key. `SUPABASE_URL` falls back to the blog's `NEXT_PUBLIC_SUPABASE_URL`.

`supabase/migrations/20261109052500_ai_photo_accounting.sql` was generated by the CLI and tested only in a temporary local PostgreSQL 17 database. It remains **unapplied to hosted environments**. Before adopting it, inspect the blog branch and remote migration history, move/resequence through the existing migration workflow if necessary, and review the private schema and RPC grants. Do not run a broad `db push` against an unknown project.

The migration creates only `ai_private.controls`, `attempts`, `rate_events`, their indexes and four `public.ai_*` RPC functions. Private tables have RLS and no anon/authenticated grants. RPCs are SECURITY INVOKER with an empty search path, and EXECUTE is explicitly revoked from PUBLIC/anon/authenticated. Only the server's service role has the required private-table access. No SECURITY DEFINER bypass, user-metadata role checks, auth tables or blog tables are involved.

The singleton accounting row defaults to **disabled**. A database owner must explicitly enable it in the development database after the migration, review and credential setup; no browser can do this. Database check constraints prevent caps above $1/day and $10/month. Application arguments cannot raise database limits. All accounting mutations lock that row, serializing reservations, duplicate checks, session limits and cost reconciliation across server instances.

Rows store pseudonymous session/IP hashes, timestamps, model, image count, token counts, cost and status. No image, file name, evidence, markings, customer description, provider body or API key is stored. Retain accounting attempts until their month is closed plus reconciliation/audit buffer; deleting current-period rows would restore spending allowance and must never happen. Unreconciled reservations must not be deleted regardless of age; reconcile trusted usage before any closed-period cleanup. Review retention/cleanup with the shared blog database owner; no automatic deletion job is installed. Rate events can be purged after their one-minute window plus a small diagnostic buffer. Rotating the session/IP hash secrets during a period resets rate identifiers; global spending remains enforced.

## Costs and cutoff

Official pricing checked 2026-11-09:

- `gpt-5.4-mini-2026-03-17`: $0.75/million input tokens and $4.50/million output tokens at first-party standard rates.
- `detail=high`, maximum 1536×1536 analysis images: `ceil(48×48×1.2)=2765` input tokens/image.
- Up to three images, 8000 conservative text/framing/schema tokens, 1800 maximum output tokens with reasoning effort `none`.
- Bound: `(8000 + 3×2765)×$0.75/1M + 1800×$4.50/1M = $0.020322`.
- **Reserve $0.03 per request**, above that maximum plus 25% margin. The static prompt/schema byte bound is checked at runtime and in tests. No arbitrary user prose goes to the model. Unknown model IDs/aliases fail closed.
- Actual verified usage reconciles the reservation downwards, including refusals/unusable responses. Caching discounts are deliberately ignored. Provider/DB failures, disconnects and ambiguous timeouts keep the conservative reservation. There is no automatic retry or refund.
- Unexpected usage/cost overruns record the cost and disable the database gate. Price/model changes require registry, SQL constraint and test updates plus reevaluation; an environment override alone cannot bypass this.

Atomic reservations enforce $1/day and $10/calendar-month in UTC including unresolved/in-flight costs. Unreconciled reservations are carried across UTC day and month boundaries until trusted usage is reconciled; the calendar changing does not silently release them. A call is denied if its reservation would exceed either allowance. Limits also include three calls/session, one active call/session, ten/day/IP, five/minute/IP/action and four globally active calls. Requests at the limit retain the manual finder. Platform firewall controls should supplement these application controls before public release. Trusted Vercel IP headers are used only on Vercel; local reviews share a local rate bucket.

Usage monitoring is available at the authenticated reviewer page through `ai_usage_summary`. Set OpenAI project alerts and a project hard spend limit separately as defense in depth; they are not substitutes for reservations and may propagate with a delay. No admin-level OpenAI key is needed in the application. Infrastructure, tax and optional regional-processing charges are separate; this implementation targets the first-party standard endpoint, not a regional endpoint or paid fallback.

Sources: [model/pricing](https://developers.openai.com/api/docs/models/gpt-5.4-mini), [vision token calculation](https://developers.openai.com/api/docs/guides/images-vision), [spend controls](https://developers.openai.com/api/docs/guides/spend-limits).

## Privacy and security

Before submission, the customer must select the exact 1–3 photos and acknowledge transfer to OpenAI. Only compressed photos are sent. Original files, filenames, free-text problem descriptions and manual details are excluded. JPEG/PNG/WebP signatures, dimensions, byte count and single-frame decoding are validated on the server, then re-encoded without EXIF/GPS. SVG/animated content, corrupted files, mismatched MIME and decompression bombs are rejected. Multipart requests are stream-capped below the Vercel 4.5 MB limit.

OpenAI calls use `store:false`, no background mode, no Files API or Conversations, no image URL fetches, no tools and no automatic retries. There is no image storage/upload service. Response/API bodies are not logged. Usage logs contain no photo content or free-text outputs. The runtime still processes bytes in memory; clearing references permits garbage collection and is not a promise of cryptographic memory erasure.

**Do not promise zero retention.** OpenAI API content is not used for training by default, but abuse monitoring may retain content up to 30 days, with documented safety/legal exceptions. `store:false` disables response application-state storage, not all provider retention. No approved Zero Data Retention configuration is assumed. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).

Requests require a valid signed reviewer cookie, exact configured Origin and HTTP Host (not Next’s normalized internal URL), same-origin fetch metadata when supplied, consent header, UUID idempotency key and persistent rate/budget slots. The reviewer token is never sent to the browser by configuration, only entered by an authorized reviewer. Anonymous visitors cannot obtain an analysis session. The deployment's body/session logs and error tooling must also be configured not to capture multipart bodies or cookies. No capture-enabled analytics SDK was added.

Prompt injection in photographs is treated as untrusted data; no tools or URLs can be invoked. Schema enums and server validation restrict outputs, and obvious compatibility/price/dimension claims inside evidence prose are rejected. These controls do not prove the observations are correct; all suggestions are visibly labeled unverified, customer confirmation is required, and real evaluation remains a release gate.

## Tests and evaluation

`npm run test:ai` runs API/schema/image/confirmation/cost tests. Database tests require `AI_TEST_DATABASE_URL` explicitly pointing to a **dedicated local database named `ai_test`**; they reset that local schema. They reject hosted URLs and do not use the application's database variables. PostgreSQL 17 tests exercise actual permissions, transactions, parallel requests, replay, UTC windows, settlement and overrun shutdown. Mocked API tests never send photos to OpenAI.

`PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium npm run test:e2e` includes the existing workflow/Guides/video regressions and new private-panel tests. The panel harness is test-only, served via Playwright interception, not a route or production fixture. `npm run test:ai:reviewer` additionally tests the actual Next application on port 3001 using a loopback-only HTTPS Data API shim backed by the dedicated local `ai_test` PostgreSQL database. It requires OpenSSL and Chromium, creates a temporary local trusted certificate (never disables TLS verification), deliberately removes the OpenAI key from its child server, and checks native reviewer login, server-rendered gating, credential-missing recovery, usage monitoring and logout. It produces real-app mobile/desktop screenshots; it cannot send photos to OpenAI. Tests check explicit consent, image compression, three-image selection, accept/reject, navigation, manual-detail preservation, refresh recovery, stale results and responsive layouts.

`npm run eval:ai` validates the small collection and checksums **without network calls**. The 12-case development collection includes six provisional family examples, four visually ambiguous examples needing expert labels, and two non-hardware color controls. Existing supplied images were visually inspected; no exact manufacturer identity or photographic authenticity is asserted. These are smoke examples, not independent field photographs or production accuracy evidence. Ambiguous cases are explicitly excluded from accuracy scoring. No existing website image mapping was changed.

Live development evaluation requires separately supplied credentials, reviewer authorization and explicit `AI_EVAL_APPROVED=true`, `AI_EVAL_ORIGIN`, `AI_REVIEW_COOKIE`, then `npm run eval:ai -- --execute`. This transfers only manifest-listed images through the same secured, metered endpoint. Session/rate/budget limits still apply; the script stops on rejection rather than bypassing limits to finish. Use `--case=case-id` to evaluate a chosen case during a later authorized session; each run writes a separate timestamped report. Reports contain family IDs and timing, not photo bytes, cookies or free-text evidence. Human review of each result is still required.

Before public release: add independent, permission-cleared real field photos for all ten families, unclear views, unsupported hardware, unrelated objects and image prompt-injection cases; obtain expert labels; separate held-out photographs by physical part/source; measure per-family top-one/top-three performance, Unknown behavior, fabricated observations, latency/cost, and follow-up usefulness. Complete real OpenAI/hosted accounting end-to-end tests and physical Android capture checks. No public accuracy claim or production release is justified by the small set or mocked tests.
